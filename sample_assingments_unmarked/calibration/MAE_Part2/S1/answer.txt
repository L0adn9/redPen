1.0 Introduction

This document discusses the SPACESHARKS Project Coordination Application that is a
cross-platform application developed with Flutter and is aimed at serving the users that are in
any of the three user roles identified during the generative research phase of Part 1, i.e.,
Owner/Manager, Content Creator/Staff, and Client. This application consolidates the
SPACESHARKS workflow that previously used status updates through messaging apps,
approvals over the phone, and manually done content scheduling.

This report covers all required deliverables for Part 2, i.e., problem-solving and design
documentation (Sections 1.0–8.0), test report (Section 9.0), user manuals for all three user roles
(Section 10.0), and workload matrix (Section 11.0). Source code, APK, and the video
demonstration of the application will be uploaded to Moodle separately.

The implementation of all 26 use cases (OM-UC1–OM-UC9, ST-UC1–ST-UC8, CL-UC1–
CL-UC9) from the proposal has been completed. Full CRUD (Create, Read, Update, and
Delete) capability is provided for packages and tasks, along with image uploading with version
control, a record of approval timestamps, and a third-party public holidays API for weekly
content scheduling.

This application is developed using Flutter 3.47 (Dart 3.13) and targets Android OS. An iOS
project is also included but has not been built or tested. In order to optimize development time
and lower the costs of building separate native apps for each platform, cross-platform
development has been used (Biørn-Hansen et al., 2018). The architecture of the application
follows the MVVM pattern and has a repository layer. Firebase Authentication and Cloud
Firestore act as the backend services for the application. Public holidays data is obtained from
the third-party API of Nager.Holidays (Nager.Holidays, n.d.). All calendar items can be
exported to Google Calendar. Testing involves usage of flutter_test for unit and widget testing
and integration_test for end-to-end testing. The source code is managed through Git and is
uploaded to GitHub, and a build is triggered automatically when the code is pushed to the
remote repository.

2.0 System Description: Problems and Solutions

All three stakeholders face a unified problem that manifests itself in scattering of status,
feedback, and approvals between different chat apps and a manual schedule. It makes it
impossible to obtain a real-time overview of a client’s package status. The following sections
describe the problems and corresponding solutions for each stakeholder category.

Owner/Manager: Managers had no overview of all client packages; therefore, operational
delays could only be detected by reviewing the schedule manually (O2) while employees’
workload was known only through actions within the Viber group (O3). Other problems
include delays in handing over the work to another person (O1) and the lack of documentation
that reflects client approvals and modifications. The app gives owners an overview dashboard
showing all open client packages, overdue actions, and things pending for approvals. It also
shows the phase of the package, current delivery status with respect to the commitment, and the
health of the package (OM-UC1, 2, 3, 8). There is a special page for workload where every
employee is classified as either overloaded, busy, or has free capacity (OM-UC4). The
handover list shows whether each file was received, and the owner can request the status update
with just one click (OM-UC7, OM-UC9). The history of approvals stores a timestamp of every
decision taken by the client (OM-UC5).

Content Creator/Staff: Staff members were not getting feedback on a unified channel (S01);
the task sheet was often out-of-date, priorities of the task were unclear, and it was not clear what
the final file version was or whether the handover was received. The app offers staff a unified
task list of all clients, a feedback thread for every task, and alerts on the modifications (ST-UC1,
2, 4). The “Do first” feature prioritises the workload by overdue tasks, change requests, and
tasks that are due within 48 hours (ST-UC3). Every uploaded file gets a version number,
handovers stay pending until confirmation by the recipient, and the approved version is marked
as the final one (ST-UC5, 6, 7). There is a weekly calendar showing the workload and a way to
notify the owner about the overload (ST-UC8).

Client: Clients were unaware of the content that was going to be delivered during the upcoming
week (P01); there was uncertainty whether their comments in the chat group were received
(P02); there was no documentation of informal approvals (P03). The app provides information
on the phase of the package (Introduction, Build-up, or Accelerated) and content that is going to
be delivered in the next seven days (CL-UC1, CL-UC2, CL-UC3). Clients can post their
comments on each deliverable and find out whether the agency has seen them (CL-UC4, CL-
UC7). Client’s approval or change requests can be posted using a dedicated button where the
name of the submitter, version, and time of the action are stored (CL-UC5, CL-UC6). In-app
notifications inform the client when his/her action is required, and a library of approved
deliverables collects all of them in one place (CL-UC8, CL-UC9).

3.2 CRUD by Role
CRUD - C = create, R = read, U = update, D = delete. On deletion of a task by the owner,
everything else related to the task is also deleted, namely comments, approvals, versions, and
handover details. Permissions checking happens at two levels: at the application level, where all
actions performed on the screen are checked against the permissions of the user, and also on the
server side using Firestore security rules (firestore.rules). These rules are automatically
checked using the Firebase emulator (Section 9.3).

4.0 Backend Database: Cloud Firestore
For the backend process, Cloud Firestore is used in conjunction with Firebase Authentication
for providing sign-in facilities for the users (Firebase, n.d.-a, n.d.-b). In particular, Firebase
provides the services for authentication and a cloud database without any server setup process
(Moroney, 2017). The data is arranged in eight top-level collections linked with the help of
identifiers. Each list in the application serves as a live listener and, therefore, when a client
approves a deliverable on their mobile phone, the dashboard of the owner and the task list of the
staff are instantly updated.

Why this architecture.

   •   Testability: ViewModels and repositories do not contain any UI code, therefore 93 unit
       and widget tests work in about 35 seconds with the in-memory database (88.4% line
       coverage), 2 end-to-end tests are run on an Android emulator, and one live test executes
       the entire flow against the live Firebase project. Since the ViewModels and repositories
       are separated from the UI, they can be tested in isolation thanks to their modularity and
       the fact that MVVM architecture simplifies testing (Andrade et al., 2025).

   •   Swappable backend: since all interactions go through DocStore, it is possible to develop
       and test the entire app before creating the Firebase project – the last step is simply
       changing one setting (--dart-define=BACKEND=firebase).

   •   Security: Firestore security rules will check the role of the logged-in user on the server
       side, so it is impossible for one client to access any data of another client outside the
       app.

8.0 Design Decisions and Limitations

8.1 Design Decisions
Each decision has been taken keeping in mind the target users studied in our Part 1 research, and
the time availability.

      A single login screen with the users/{uid} having their own role. Each of these three
       roles will have the same login procedure (as in proposal Figure 4), and then there will be
       verification of their security rules once again.

      All roles will get identical Task Detail page with information according to the role of
       individual users. Consistency in the screens ensures that clients see Approve / Request
       changes, staff sees Upload / Send for approval / Hand over, and the Owner sees Edit /
       Delete / Request status.

      Alerts within the app as opposed to Push Notifications. Since the alerts will be stored in
       Firestore, they will be retained even when the device is offline and testable. Push
       Notifications (Firebase Cloud Messaging) is for future work.

      A Public holiday API and an “Add to Google Calendar” link as opposed to a Full
       Google Calendar Sync. Full sync will mean that all the users have to sign into Google
       (OAuth). While the Nager.Holidays API does not need any key, in addition to this, it
       offers the feature of "Add to Google Calendar" link allowing anyone to add anything to
       their Google calendar.

      Responsive Design for mobiles and tablets: bottom tabs on mobiles and navigation rail
       with multicolumn grid and width of content typical of tablets.

      Input validation of forms all the way: required fields, character limit, number range, no
       due date in past, publish date after the due date, and reason for change request.

      The recommended palette of our proposal: black and white of the logo for grey cards
       with hints of orange for actions, green for accepted, amber for awaiting, and red for
       overdue.

8.2 Limitations and Future Work
      Tests were conducted only for the Android app. On the other hand, iOS project exists
       but was not installed as no Mac machine with Xcode is available.

      File size cannot exceed 700 KB without the Blaze plan. Cloud storage must be used for
       large files such as long videos.

      Notifications are done in-app. When Firebase Cloud Messaging is used, notification
       will also be sent directly to the user's phone.

9.0 Automated Test Report

from automated runs on GitHub Actions and through an Android emulator. Automated testing
is selected as it can be repeated when the app changes and is able to spot defects overlooked by

Manual testing was applied only for the app testing on the phone; every piece of information
presented in this section is based on the results of automated testing.

12.0 Conclusion and Recommendations

12.1 Conclusion
The SPACESHARKS Project Coordination App addresses the issue identified in our Part 1
research: information regarding status, feedback, and approvals was dispersed through many
chats and manual schedules. Now the owners of the packages are using the same dashboard to
track the health and progress of every package, the staff know what it is important to do and
pass the work with an implementation confirmation, and the clients approve or request
modifications with a record containing an exact time of any case. All in all, 26 use cases are
implemented with the use of Firebase Authentication and Cloud Firestore together with role-
based security rules, uploading images with versioning and public holiday API. The app is
based on 108 automated tests, including an end-to-end live test on the real Firebase project.

12.2 Recommendations
Our recommendations are as follows (in order of importance):
           1. Implement push notifications via Firebase Cloud Messaging. Notifications
              are only sent when the app is active; this system would immediately inform both
              crew members and clients about all recent activities and requests.
           2. Transfer files to Firebase Cloud Storage (Blaze plan). This way, file size
              limitations would be lifted, allowing for easier access to reels and videos.
           3. Allow the owner to send invitations to staff and clients via email. Currently,
              only the owner/demo loader has this ability; once implemented, it would allow
              new clients to obtain services on their own.
           4. Perform testing of the iOS version. The Flutter project already includes
              support for iOS, but testing requires Mac with Xcode and an actual TestFlight
              session with real users.
           5. Provide clients with monthly report exports (PDF). Such an option could
              allow owners to deliver reports to clients, outlining materials and delivery
              timelines.
           6. Two-way Google Calendar sync. Today items are added one at a time by link;
              syncing with Google sign-in would keep the content calendar and personal
              calendars aligned.
           7. Usability testing with SPACESHARKS staff and two clients. Measure task
              completion and satisfaction with the System Usability Scale (Brooke, 1996) and
              refine the screens before launch.
